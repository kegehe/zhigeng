# ADR-004 · 长文档策略：不做多实例分节，改装饰惰性化 + 拆分阈值

**状态**：已采纳（2026-09-22，M0 Spike C 实测后推翻原方案）

## 背景

[03] §大文档策略原本写："ProseMirror 不支持块虚拟化，一篇 3000 块的笔记必卡，因此按标题分节、只挂载可视节的编辑器实例"。
Spike C 用 3000 块合成文档（30 节 × 100 块）在 Chromium 里实测，前提是"重排会随 DOM 规模线性变贵"。这个前提**没被数据支持**。

## 实测数据（`probes/spike-c/`，隐藏窗口 + 强制同步布局，只量纯重排成本）

| 场景 | DOM 节点 | 每次输入的重排 p50 / p95 |
|---|---|---|
| A 全部挂载（单实例，3000 块） | 3001 | **4.8ms / 8.7ms**（首次冷布局 149ms） |
| B 分节挂载（3 个实例，330 块） | 330 | 0.7ms / 1.7ms |
| 分节的额外代价：一个 100 块节的卸载 + 挂载 | — | 卸载 1.8–8.5ms + 挂载 5.9–11.7ms ≈ **每次跨节 9–20ms** |

结论：A 模式 3000 块下的**输入重排成本本身在预算内**（G6 要求 < 16ms）。分节把 4.8ms 降到 0.7ms，收益存在但不是数量级，而且每跨一节要付 9–20ms。

## 为什么仍然要做事（但换个做法）

真正随 DOM 规模线性增长的不是重排，而是**样式重算、绘制、选区计算，以及 ProseMirror 自己的装饰层与状态映射**——这些本原型没有量到，也恰恰是实测最容易低估的部分。所以：

| 选项 | 决定 |
|---|---|
| A. 多实例分节（原方案） | **不做**。代价已被证明不划算：跨节选区与拖拽要砍（体验损失）、撤销栈要跨实例打通（复杂度）、每跨节 9–20ms，换来的只是 4ms → 0.7ms |
| B. **单实例 + 装饰惰性化**（采纳） | 保持一个编辑器实例。可视区之外不挂 Decoration（语法高亮、行内标记、搜索命中框），滚动时增量补挂。拿到装饰层的规模收益，不动选区与撤销模型 |
| C. 拆分阈值（采纳，配合 B） | 单篇 > 1500 块时由 AI 提 `split` 建议（不自动拆），UI 明确提示。这是产品手段而不是渲染技巧，成本几乎为零 |
| D. 分节仍保留的唯一用途 | `md_kernel.heading_sections()` 继续存在并已实现，用于**目录面板、按节跳转、节级折叠**，不用于编辑器实例切分 |

## 代价与复测要求

本测法有两个已知局限，写下来防止后人把这份数据当结论的结论：

1. 窗口是 `visibilityState: hidden`，rAF 被饿、caret-into-view 等不到合成帧——**前两种测法分别拿到了 43s 与 5.9s 的假尖峰**。因此本轮只采用"直接改文本节点 + 强制同步布局"的测法，它量的是纯重排，不含绘制与合成。
2. 原型是裸 `contenteditable`，**没有 ProseMirror 的装饰层、选区与事务开销**。真实编辑器的每键成本必然高于 4.8ms。

所以定稿前必须做一次真机复测：在 Tauri 壳（可见窗口）里用真 TipTap 实例，量 3000 块文档的输入延迟与滚动掉帧，并把数字记进本 ADR。若真机 p95 超 16ms，回到选项 B 的加强版（按节切分 Document 但保持单实例，用 ProseMirror 的 `slice`/`replaceWith` 做局部刷新）。

## 复测进展（2026-09-24）：先被无损往返挡住，重做后测完了

真机复测**还没有发生**，因为 TipTap 实例还没安全接到用户文件上。第一轮尝试（一个块 = 一个 ProseMirror
节点、未改动的块原样回写 `raw`）在真机上跑了字节级测试，结果是**编辑一次就把整篇吃掉**：
658 字节的样本存成 410 字节——锚点全丢、`##` 降级成 `#`、嵌套列表拍平、待办变普通条目、
引用/代码/表格整块消失。已把该实现从界面上撤下，编辑退回已验证无损的整篇源码模式。

**门槛已经立住了**：`src/editor/roundtrip.test.ts`（`pnpm test`，jsdom，不启窗口、不碰用户文件）
吃 `note edit-doc` 导出的 5 个真实语法样本夹具，22 条断言全绿——每个样本四条：Rust 侧拼装等于
源文件、进编辑器什么都不改等于源文件、改一个字再撤销等于源文件、同一篇连算两次产出不变；
外加空笔记与"勾选待办必须落盘"。夹具本身由 `service.rs` 那条测试钉住不与解析器脱节。

第一轮那三条根因，实测下来是四条，全部有据：

1. **块间空白是 `gap_before` + 块自带结尾换行共同表达的**。回写时对 `raw` 做了
   `trimEnd()`，相邻列表项之间那个换行就没了，整篇塌成一段。
2. **签名比对必须由同一个函数在"装载后的活节点"上算**。手写 JSON 多一个 `marks: []`
   就对不上；而 `sigOf` 就地 `delete` 更狠——`node.toJSON().attrs` 就是节点活着的那个对象，
   删键等于把 `mdRaw`/`mdSig` 从文档里抹掉：**第一次保存正常，第二次保存全部块成"新块"、
   整篇重写**，这正是 658→410 的形态。
3. 上一轮"节点属性装载后是空的"根因找到了：**StarterKit 的同名节点（paragraph/heading）把
   自定义节点顶掉**，实际节点类型没声明 `md*`，ProseMirror 装载 JSON 时静默丢弃。
   现在 schema 自己声明 `doc`/`text` 与四个块节点，一行 StarterKit 都不引。
4. 新增加的一条：**`EditBlock.content` 不含 `due::`/`done::` 行内字段**（与索引同口径），
   所以按它重新产出这一块会把用户的到期日洗掉。夹具改不了这一点，是测试把它逼出来的——
   现在 `EditBlock` 带 `fields`，序列化按 `render_block` 的口径写回。另外**嵌套子项的字节算在
   父项的 `raw` 里**（子项 `raw` 不带缩进），所以块编辑器的粒度只能是 md-kernel 的顶层块，
   把子项提成兄弟节点必然重复字节。

**顺序执行到了这里**：门槛绿（`pnpm test` 23 项，含一条 3000 块的规模用例）→ 编辑器接上界面
（真机验证一次编辑只改那一行）→ 3000 块真机测量，结果见下一节。

## 真机测量结果（2026-09-24，release 构建 + WebView2 CDP）

样本是 `D:\Notes` 里造的 2999 块 / 490KB 笔记（段落、`##` 标题、列表、代码围栏混排，
每段带一条站内链接），对照样本是同库的 8 块笔记。测量方式是 CDP 发**可信**按键，
用 Event Timing 读"输入到呈现"——`execCommand` 那种合成事件不算用户输入，量不出来。

| 指标 | 8 块对照 | 2999 块 | 预算 |
|---|---|---|---|
| 打开编辑器（点编辑到首屏） | 27ms | **297ms** | G7 要求 100ms 内有反馈 |
| 打字到屏幕 p50 | 16ms | **24ms** | 16ms |
| 打字到屏幕 p95 | 32ms | **32ms** | 16ms |
| 事件处理（JS）p95 | — | **0.2ms** | 8ms |
| 连续滚动 120 帧里 >32ms 的 | — | **0 帧**（最差 18ms） | 掉帧率 1% |
| 一次保存后第一个同步读命令 | 126ms | 22954ms → **2064ms**（补外键索引后） | 8ms |

结论分三条：

1. **"滚动不掉帧"达成**，且与块数基本无关——ProseMirror 的视图更新很便宜（CPU profile 里
   一次击键的自有 JS 只有 2–3ms，其余是浏览器原生布局）。**单实例这条路没被推翻**。
2. **"打字 P95 < 16ms"这条预算写法有问题**：60Hz 下一次呈现的最小间隔就是 16.7ms，
   连 8 块的对照样本 p95 都是 32ms。可测的口径应是"输入到呈现 ≤ 1 帧"或"事件处理 < 8ms"，
   后者我们 0.2ms 达标。3000 块相对对照样本多出的正好是一帧（p50 16→24ms），
   来源是浏览器对约 3000 个同级块的重排，不是我们的代码。
3. **真正卡住长文档的不是编辑器，是索引**：保存一篇 490KB 的笔记后，同步读命令要等 22.5 秒。
   根因是 `blocks.parent_id` / `chunks.start_block` / `chunks.end_block` 这三条外键没有索引，
   增量索引要先删 2999 行，每删一行 SQLite 就在这些表上全表扫一次。补索引后降到 2.06 秒
   （1500 块 22.6s → 1.37s）。**剩下的 2 秒仍然握着 Hub 的锁**，切笔记预算 80ms 照样顶穿——
   下一步是把 `index_one` 包进一个事务，并且让读命令不必等这把锁。

代价与修正：本 ADR 原先把"分节渲染 / 1500 块拆分阈值"当作长文档的前提，测下来
**打字与滚动都不需要靠拆分达标**，需要的是把索引从读路径上摘下来。拆分阈值先不动，
等"打开编辑器 297ms"这条真觉得慢了再说（G7 的 100ms 靠先给反馈解决，不靠拆文档）。

## 真机复测（2026-09-29，本周 UI 做完之后，`pnpm tauri build` 的 release + CDP 可信输入）

样本：临时造的两篇放进 `D:\Notes`——2999 块 / 270KB（段落、`##` 标题、列表、` ``` ` 围栏混排，
每段带一条站内链接）与 8 块对照。**测完删除，事后 `reindex --dry-run` 报 0 漂移 0 孤儿，
整库 sha256 与测前逐字节一致**。开测前断言 `visibilityState === 'visible'`（Spike C 那条纪律）。

| 指标 | 8 块对照 | 2999 块 | 预算 / 口径 |
|---|---|---|---|
| 打开到首屏 | 54ms | **264ms** | G7 要 100ms 内有反馈（骨架屏顶着） |
| 输入到呈现 p50 | 24ms | **24ms** | —— |
| 输入到呈现 p95 | 32ms | **32ms** | 写法不成立（见下），改按"≤ 一帧"判 |
| 事件处理 p95（Event Timing `processingStart→processingEnd`） | 1.8ms | **10.2ms** | 8ms，**超** |
| 连续滚动 ~100 帧里 >32ms 的 | 0（最差 19ms） | **0（最差 19ms）** | 掉帧率 < 1%，**达成** |
| INP（这次即输入到呈现 p95） | 32ms | **32ms** | < 50ms，**达成** |

同步 IPC 命令（12 次取分位，同一台机、同一份库）：`list_notes` p50 0.9 / p95 2.1ms，
`read_raw` 4.1 / 5.3ms，`search_keyword` 1.6 / 3.3ms，**`note_edit_doc` 13.5 / 15.0ms**
（它要把整篇 270KB 重解析成块结构，超 8ms 预算——但它是"打开一篇"的成本，不是打字路径上的）。

**三条结论**：

1. **本周那些界面活（显示形、表格网格、图标工具栏、粘贴）没有让打字变慢**：2999 块与 8 块对照
   的输入到呈现**逐分位相同**（24 / 32ms）。9-24 那次量到"长文档比对照多一帧（p50 16→24ms）"，
   这次这个差值消失了。
2. **"打字 P95 < 16ms"这条预算写法仍然不成立**：对照样本的 p95 也是 32ms（60Hz 下一次呈现最小
   间隔 16.7ms，两帧就是 32）。维持原判定，按"输入到呈现 ≤ 一帧"或"事件处理 < 8ms"两条来判。
3. **10.2ms 那条与 9-24 记的 0.2ms 不是同一个量**，别读成"退化了 50 倍"：Event Timing 的
   `processingEnd - processingStart` 含事件处理**内同步触发的布局**，而 CPU profile 显示这 10ms 里
   大头是浏览器自己（下条）。口径不同的两个数不许直接比——这条写下来是因为我自己第一反应就误读了。

CPU profile（2999 块、80 次可信按键、窗口 4882ms，按 `samples`+`timeDeltas` 算自身耗时）：
`(program)` 645ms ≈ **8ms/键**（浏览器对约 3000 个同级块的重排）、匿名 JS 151ms ≈ 1.9ms/键、
GC 51ms、**`appendTransaction` 10.5ms ≈ 0.13ms/键**。最后一行是刻意量的：账本守卫每次事务都要
走一遍文档，我怀疑过它是 10ms 的来源，profile 直接否掉了——**别把"看起来像新加的"当成原因**。

顺带一条与性能无关但同一次测量撞出来的缺陷：**命令面板的「新建笔记『X』」排在标题命中项前面**，
探针按 `↓`+`Enter` 打开样本时实际**建出了一篇新笔记**（已删）。有命中还把"新建"顶在第一行，
等于让回车默认做破坏性动作——记在 [05] 欠账里。
