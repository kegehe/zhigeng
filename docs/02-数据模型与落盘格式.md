# 02 · 数据模型与落盘格式

> 全项目唯一不可逆的决定。改错了，后面所有 AI 能力都建在错误的地基上。动工前先评审这一篇。

## 设计目标

同一份数据要同时是四种东西，不能为其中一种牺牲另一种：

1. **人可读的文档** —— 用户用 Obsidian / VSCode / git 直接打开编辑，不锁格式
2. **可寻址的知识单元** —— 每个块有稳定 ID，AI 的每条引用都能精确点回原文
3. **一张图** —— 笔记与块之间的链接是显式关系，供图谱与检索扩展使用
4. **RAG 语料** —— 可切片、可嵌入、可增量重建索引

## 四条数据层不变量

对应 [00-文档导航.md](./00-文档导航.md) 的 G1 / G5 在此层的细化。

| # | 不变量 | 违反后果 |
|---|---|---|
| I1 | Markdown 是用户笔记内容的唯一真相源，`index.db` 是纯派生物（例外见 §I1 例外清单） | 用户资产被自有格式绑架，本地优先名存实亡 |
| I2 | 删掉 `index.db` 必须能靠扫描 Vault 完整重建（设计上限 2 万篇 < 60s，不含嵌入；口径见 [03] §性能预算） | 索引腐烂后无法自救 |
| I3 | 方向只有 `md → db`。**永不**从 db 反向写 md（用户显式保存、接受建议、首次分配块 ID 除外） | 静默覆盖用户手改内容 |
| I4 | MD ↔ 编辑器模型字节级无损往返 | 用户其他编辑器里的内容被"保存"操作吃掉 |

### I1 例外清单（允许只存在于 `index.db` 的数据）

判据：**是不是用户亲手写下的内容**。以下不是，所以允许只在库里，删库后丢失属预期行为：

- 派生索引：分词结果、嵌入向量、切片边界、链接图的解析缓存
- AI 过程数据：`suggestions`、`ai_runs`、`jobs`、对话记录
- 性能缓存：缩略图、解析中间产物

**反例（必须能从 Vault 的 md 文件或目录结构中还原）**：笔记正文、标题、标签、属性、用户手写的链接、归档状态（= 所在目录）、视图定义（= `views/` 下的文件）。写代码时想往库里塞一张"只有 db 有"的用户数据表，必须先回来改这份清单。

## Vault 目录结构

用户选定一个文件夹作为 Vault（如 `D:\Notes`）。

```
<Vault>/
  inbox/                      # 未整理的快速捕获区，AI 整理任务的输入
    2026-09-22-standup.md
  notes/                      # 正式笔记，用户可自由建子目录，无限层级
    ai-native/
      主动层设计.md
      检索策略.md
    reading/
      2026-09-22-x 文章标题.md
  archive/                    # 归档（不是删除；移动即生效）
  views/                      # 动态视图 / 智能集合的定义文件（见 §视图与智能集合）
  attachments/                # 二进制资产，内容寻址命名，必须随 Vault 备份
    a3/a3f9c1e2....png
  .note/                      # 应用私有
    index.db                  # SQLite：FTS + 向量 + 图 + 建议箱 + 任务（可删可重建）
    trash/                    # 回收站：按原相对路径存放，清空即真删
    conflicts/                # 外部修改冲突时保留的磁盘版本，供用户手动比对
    versions/                 # 内容快照（gzip），撤销与历史依赖它
    config.toml               # 模型、自动化档位、快捷键（删除后需重配，但不丢用户内容）
    secrets.keyref            # 只存"Windows 凭据管理器条目名"，不存 key 本身
    cache/                    # 缩略图、解析中间产物
    logs/                     # 按日滚动，保留 14 天
```

**`.note/` 内部两分**：`index.db` / `cache/` / `logs/` 是可再生层（删了自动重建）；`config.toml` / `secrets.keyref` / `trash/` / `conflicts/` / `versions/` 是需重配或不可丢层。**判据始终是同一条：删掉会不会让用户丢内容。** 备份指引里必须明确"Vault 整体复制即可完整迁移"。

资产用 SHA-256 内容寻址命名 → 天然去重，同一张图被多处引用只存一份；原始文件名保留在 `attachments.orig_name`（派生，丢了可从 md 引用处重新解析）。

### 扫描与排除规则

索引扫描器遍历 Vault 时的规则，写错一条就会出现"回收站里的笔记被 AI 引用"这类恶性 bug：

| 路径 | 是否索引 | 是否可被笔记链接到 |
|---|---|---|
| `notes/`、`inbox/`、`archive/`、`views/` | 建 `notes` 行（`archive/` 默认从检索结果排除，可显式包含）；**`views/` 只登记为 `note_kind='view'`，不进 `blocks`/`chunks`/FTS/向量**（见 §视图与智能集合） | 是 |
| `attachments/` | 只入 `attachments` 表，不产生 `notes`/`blocks` | 是 |
| `.note/` 及其全部子目录（含 `trash/`、`conflicts/`、`versions/`） | **一律不索引** | 否 |
| 任何以 `.` 开头的目录、`node_modules/` | 不索引 | 否 |
| 非 `.md` 的未知扩展名 | 不索引，但作为资产登记 | 是 |

**回收站的索引处理**：笔记移入 `.note/trash/` 时，同步删除其 `notes` 行（连带 `blocks`/`chunks` 级联与派生表清理），并在 `note_versions` 写一条 `reason='before_delete'` 快照；恢复时移回原路径重新解析。回收站列表本身由扫描 `.note/trash/` 目录得出，不存 DB 状态。

### 资产引用格式

**资产一律用 Vault 根相对的 Wikilink 引用**：`![[attachments/a3/a3f9c1e2....png]]`。

不用 `../attachments/xxx.png` 这类相对路径——笔记自身所在层级不同，相对前缀就不同（`notes/a/b.md` 需要 `../../`），手写和跨编辑器迁移都极易断链。前导的 `attachments/` 前缀配合内容寻址文件名，保证移动笔记不断链。解析器同时**兼容**用户从 Obsidian 带来的相对路径写法，并在解析后归一化。

## Markdown 扩展约定

基底是 **CommonMark + GFM**，只增加四处约定：块 ID、Wikilink 链接、Callout、front-matter 扩展字段。除此之外**不许发明私有语法**——每加一条私有语法，就多一分与其他编辑器互不兼容的债。

### 块 ID（Obsidian 兼容语法）

块 ID 追加在块末行尾部：` ^b-<10 位小写字母数字>`（详细选型论证见 [adr/ADR-002-块ID语法.md](./adr/ADR-002-块ID语法.md)）。

- 选 `^b-xxx` 而非 `{#xxx}`：**双向兼容**是本地优先的命脉。用户在 Obsidian 写的 `[[笔记#^b-xxx]]` 我们直接认，反之我们的链接他在 Obsidian 里能跳。
- 代价：不支持块 ID 的渲染器（如 GitHub）会把尾部 `^b-xxx` 当正文显示。可接受，且导出 HTML 时统一剥离。
- 代码块、表格、Callout 等无法在末行内追加时，ID 独占一行写在块之后。
- 无 ID 的块（用户手写、导入）在首次索引时自动分配 ID 并回写一次。**回写前必须弹窗告知**，因为这是"应用改动用户文件"。
- ID 一经分配永不复用、永不因移动或编辑而改变。删除块则 ID 作废，指向它的链接变悬空链接（UI 标红，不自动删）。
- **冲突规则**：两个文件带同一 `id`（用户直接复制文件导致）时，路径字典序靠前者保留 ID，后者重新分配并在建议箱提示"检测到复制的笔记"。

### 链接

| 语法 | 含义 |
|---|---|
| `[[笔记名]]` 或 `[[notes/子路径/笔记名]]` | 笔记级引用 |
| `[[笔记名#^b-xxxxxxxxxx]]` | 块级引用（AI 溯源用这个） |
| `[[笔记名#一级标题]]` | 标题锚点 |
| `![[笔记名]]` | 嵌入，渲染时内联展开 |
| `[[笔记名` + 竖线 + `别名]]` | 带显示别名（Obsidian 竖线语法） |

相对路径链接 `[文本](./a.md)` 与外链一并解析入图。

### 块类型（v1 共 15 种）

全部必须能用 Markdown 无损表达，这是"不锁格式"的硬约束（G1）。

| type | Markdown 表示 |
|---|---|
| `paragraph` | 普通段落 |
| `heading` | `#` 至 `######` |
| `todo` | 减号加空格方括号，`- [ ]` / `- [x]`；到期与完成时间见 §待办的到期约定 |
| `bullet` | 无序列表项，嵌套层级由 `parent_id` 表达 |
| `numbered` | 有序列表项，嵌套同上 |
| `quote` | 引用块 |
| `callout` | Obsidian 风格 `> [!note]` |
| `toggle` | 折叠式 Callout（`> [!note]- ` 形式） |
| `code` | 三反引号围栏 + 语言标识 |
| `table` | GFM 表格 |
| `math` | `$$` 块级公式 |
| `image` | `![[attachments/a3/xxxx.png]]`（见 §资产引用格式） |
| `file` | 指向非图片资产的链接 |
| `embed` | `![[...]]` |
| `divider` | 独占一行的 `---` |

**`---` 的解析优先级**（三处冲突必须固定规则，否则往返有歧义）：文件第一行的 `---` 是 front-matter 起始边界；紧随段落之后的 `---` 按 GFM 规则优先解析为 setext H2 下划线（**保持 GFM 行为，不改**）；其余独立成段且前后为空行的 `---` 解析为 `divider`。编辑器写入分隔线时总是补空行。

白板、内嵌数据库渲染、批注层高亮 → v1 明确不支持，因为它们无法无损落成 Markdown。

### 兜底类型 `raw`（第 16 种，仅内部使用）

超出上述 15 种、或解析器不认识的块（其他编辑器带来的私有语法、HTML 片段、未知指令），一律解析为 `raw` 类型：**原样保存源文本，UI 只读渲染为等宽灰底代码块，编辑器不解析其内部结构**。

`raw` 是 G5（无损往返）的最后防线——丢内容永远比丢类型严重。配套两条硬规则：

1. `raw` 块**不进 AI 上下文**（语法未知的内容容易带隐私标记或指令注入文本），且计入索引健康报告的"未识别块数"，非零时在设置页可见
2. AI **不得对 `raw` 块提 `restructure`/`split` 建议**（不认识就无法保证改写正确）

### 视图与智能集合（`views/`）

"把一次语义查询存成动态目录"是用户创造的内容，删库后必须能还原，所以**不能只存 DB**，也不能新增私有格式——复用笔记机制：

```md
---
id: n-v12mk8pq
title: 待整理的 AI 原生想法
view:
  kind: smart            # smart（语义/条件查询）| table | board | calendar
  query: "AI 原生"
  filter:
    tags: [ai-native]
    status: inbox
  sort: created desc
  limit: 200
---
```

`views/` 下的文件有 `view` 字段即被识别为视图而非普通笔记：不出现在正文编辑器里，渲染为动态列表。查询结果每次实时算，**绝不缓存成"看起来是数据"的表**，所以它对 I1 完全无负担。

三条配套规则，避免它变成"其实我们支持了内嵌数据库"：

- 视图文件**不参与检索、不进 AI 上下文**（它是查询定义，不是知识内容；否则一个"待补清单"视图会反复污染 gap_scan 的结果）
- v1 **不支持在正文里 `![[views/xxx]]` 嵌入视图**。这与"不支持内嵌数据库渲染"是同一条决心的两面：视图只在独立页面与侧栏打开
- 视图渲染时读取的是实时查询，所以视图本身永不需要"保存结果"，也不产生 diff 冲突普通静态视图（按标签/属性筛选的表格、看板、日历）同样落在这里。

### front-matter（YAML）

只放用户拥有且看得懂的元数据。**派生物（嵌入向量、分词、摘要缓存）一律不进 front-matter**，避免污染文件和 diff。

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | `n-` + 8 位；文件改名/移动都不变，用于认亲 |
| `title` | 否 | 缺省时取首个 H1，再缺省取文件名 |
| `tags` | 否 | 扁平标签数组 |
| `created` | 是 | 首次写下时间，AI 判断"我什么时候想过这个"的依据 |
| `props` | 否 | 任意键值，属性/看板/日历视图的数据源。保留键见下表 |
| `ai.private` | 否 | `true` 时该笔记任何块不得进入 AI 上下文 |
| `ai.no_ai` | 否 | 连摘要、打标都不做（比 private 更严格） |

**`props` 保留键**（有语义，UI 会区别对待；其余键是用户自定义）：

| 保留键 | 含义 |
|---|---|
| `as_of` | 该笔记内容的"截至何时我认为为真"。AI 判断信息陈旧、`resurface` 决定"三个月前想过"都读它；缺省回落 `created` |
| `source_url` / `fetched_at` | 网页剪藏来源，写入即代表**内容来自外部**（影响 `origin` 与注入防护，见下） |
| `due` | 见 §待办的到期约定 |

### 待办的到期约定

`gap_scan` 要判断"待办已过期"，但 CommonMark/GFM 的 `- [ ]` 里没有日期位置。约定用社区已有的 **`key:: value` 行内字段**（Obsidian Tasks / Dataview 的既有语法，不是我们发明的私有语法）：

```md
- [ ] 把主动层的触发点定下来 due:: 2026-09-28 ^b-t6j9l2n5ey
```

- 解析进 `blocks.props_json`（`{"due":"2026-09-28"}`），渲染时从可见文本里剥离并显示成日期胶囊
- **只识别 `due::` 与 `done::` 两个键**，其余 `key::` 一律当普通文本，不做任何猜测——社区约定没有注册表，猜错就是吃掉用户内容
- 未知键原样保留，序列化时按原文写回（G5）

### 内容来源 `origin`

派生列，不落 front-matter：有 `props.source_url` 或来自导入 → `clipped` / `imported`，否则 `human`。

它存在的唯一理由是 [04] §全局契约的注入防护需要能**在 SQL 层**区分"用户自己写的"和"从网上扒来的"，而不是靠模型自觉。

**没有 `status` 字段。** 状态权威是**文件所在目录**：`inbox/` → inbox，`archive/` → archived，其余 → active。把状态同时写进 front-matter 和目录会造成双真相，必然漂移。DB 的 `notes.status` 是解析时推导出的缓存列。

**没有 `updated` 字段。** 每次保存都改 front-matter 会造成 git diff 噪音；更新时间由文件 mtime + DB 记录承担。

## 索引层 Schema（SQLite）

`<Vault>/.note/index.db`。WAL 模式，`foreign_keys=ON`。

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- 必存：schema_version, md_format_version, vault_id, jieba_dict_version,
--       last_full_reindex_at, active_embedding_model

CREATE TABLE notes (
  id           TEXT PRIMARY KEY,          -- front-matter id
  path         TEXT NOT NULL UNIQUE,      -- 相对 Vault，正斜杠
  title        TEXT NOT NULL,
  note_kind    TEXT NOT NULL DEFAULT 'note',  -- note | view（views/ 下的动态视图定义）
  status       TEXT NOT NULL DEFAULT 'active',  -- 派生自所在目录，不写回 md
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,             -- 来自 mtime
  content_hash TEXT NOT NULL,             -- 整篇 sha256，判增量与陈旧
  ai_private   INTEGER NOT NULL DEFAULT 0,
  no_ai        INTEGER NOT NULL DEFAULT 0,
  origin       TEXT NOT NULL DEFAULT 'human',  -- human|clipped|imported，派生；AI 注入防护靠它过滤
  -- 为未来多端同步预留，第一版不写值；加列比改表便宜
  rev          INTEGER NOT NULL DEFAULT 0,
  device_id    TEXT
);

CREATE TABLE blocks (
  id            TEXT PRIMARY KEY,          -- b-xxxxxxxxxx
  note_id       TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  parent_id     TEXT REFERENCES blocks(id) ON DELETE CASCADE,  -- 列表嵌套
  ordinal       INTEGER NOT NULL,          -- 文档顺序
  type          TEXT NOT NULL,
  heading_level INTEGER,
  text          TEXT NOT NULL,             -- 剥离语法后的纯文本（可为空串）
  markdown      TEXT NOT NULL,             -- 原始片段，含块 ID 标记
  line_start    INTEGER NOT NULL,
  line_end      INTEGER NOT NULL,
  props_json    TEXT,                      -- 类型专有属性：语言/勾选态/URL/alt
  UNIQUE (note_id, ordinal)
);

-- RAG 检索单元：1..N 个连续块组装成 200–800 token。
-- 单块太小缺上下文，整篇太大浪费预算。
CREATE TABLE chunks (
  id          INTEGER PRIMARY KEY,
  note_id     TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  start_block TEXT NOT NULL REFERENCES blocks(id) ON DELETE CASCADE,
  end_block   TEXT NOT NULL REFERENCES blocks(id) ON DELETE CASCADE,
  header_path TEXT,                        -- "主动层设计 > 触发点"，作上下文前缀
  token_count INTEGER NOT NULL,
  text        TEXT NOT NULL,               -- 含前缀的实际嵌入文本
  source_hash TEXT NOT NULL                -- 变了就重嵌
);

-- 全文检索：FTS5 的 unicode61 不分中文词，必须由 jieba-rs 预分词后写入 seg 列。
-- 刻意用独立 FTS 表（自带内容）而非 external-content 表：重解析一篇笔记时
-- 只需 DELETE + INSERT，不必维护触发器与影子表，少一类"索引和主表不一致"的 bug。
-- rowid 显式对齐 blocks.rowid / chunks.rowid。
CREATE VIRTUAL TABLE blocks_fts USING fts5(
  seg, tokenize="unicode61 remove_diacritics 2"
);
CREATE VIRTUAL TABLE chunks_fts USING fts5(
  seg, tokenize="unicode61 remove_diacritics 2"
);

-- 向量：每个嵌入模型一张 virtual table，换模型 = 建新表 + 全量重嵌。
-- 语法为 vec0（旧文档里的 vec_embeddings 已废弃，见 ADR-003）：
-- CREATE VIRTUAL TABLE vec_bge_m3 USING vec0(embedding float[1024]);
-- vec 表 rowid 与 chunks.id 对齐；向量以小端 f32 拼成的 BLOB 传入。
-- 扩展经 sqlite3_auto_extension 静态注册，不分发 .dll，且全仓库禁止 load_extension。
CREATE TABLE embeddings (
```

### 派生表的手工清理（易错点）

FTS5 与 sqlite-vec 的 virtual table **不参与外键级联**。重解析或删除一篇笔记时，`blocks`/`chunks` 会随 `ON DELETE CASCADE` 消失，但 `blocks_fts`、`chunks_fts`、`vec_*` 里的行会残留成孤儿，导致检索命中已不存在的内容。

因此**每次笔记级重建必须按顺序显式执行**：

1. 先查出该笔记所有 `blocks.rowid` / `chunks.id`（此时主表还在）
2. 用上一步的 id 删 `vec_*` 行 → 删 `blocks_fts` / `chunks_fts` 行（`WHERE rowid = ?`）
3. 删 `chunks` / `blocks`（外键级联）→ 重新插入 → 重建 fts 与 vec 行

**步骤 1 不能省**：`blocks` 的 rowid 是隐式行号，一旦先删了主表就再也找不到对应的 fts 行，孤儿必留。全量重建则直接 `DROP` 后重建 fts 与 vec 表，比逐行删快一个数量级。这条要在 `index` 模块用单测覆盖：删一篇笔记后跑一次全库检索，命中数必须归零。

## 写入与外部修改

**保存路径**：写临时文件 → `FlushFileBuffers` → `ReplaceFile`（原子改名）→ 重算 hash → 增量重建该笔记索引 → 写 `note_versions` 快照。崩溃不产生半截文件。

**外部修改**（用户在 Obsidian/VSCode 里改了文件，`notify` 监听到）：

| 情形 | 处理 |
|---|---|
| 本地无未保存改动 | 直接重解析该文件，UI 刷新 |
| 有未保存改动，且磁盘 hash ≠ 我们上次写入的 hash | 冲突：保留双方，磁盘版本落 `.note/conflicts/` 并提示，**绝不静默覆盖** |
| 仅 mtime 变化、hash 相同 | 忽略（编辑器自动保存噪音） |

改名与移动按 `id` 认亲，不按路径，避免链接图断裂。找不到 `id` 时退化为按"路径 + 内容 hash 相似度"匹配。

**删除**：移动到 `.note/trash/<原相对路径>`，恢复即移回。清空回收站才真正删文件。状态存于目录本身而非 DB 列，同样是为了不违反 I1。

## 版本与迁移

- `schema_version`（整型）：DB 结构版本。破坏性变更走"删库重建"——索引是派生物，**不写迁移脚本，只写重建器**。
- `md_format_version`：块 ID / front-matter 约定版本。**这个必须写迁移脚本**，因为它长在用户资产里。v1 → v2 需 dry-run + 全量备份后再改。
- 重建器与增量解析器必须共用同一份 `md-kernel` 代码路径（`reindex = parse(all files)`），杜绝"重建出的索引和增量更新的不一致"。
- 遇到无法解析的块：降级为 `raw` 类型原样保留，规则见 §兜底类型 `raw`。丢内容永远比丢类型严重。

## 实现回写的偏差（M0 落地时发现，已同步到代码与测试）

规格写的是意图，代码会暴露意图里没定义的东西。以下每一条都是实现时被迫做的决定，**不是自由发挥**：

| # | 偏差 | 原因 |
|---|---|---|
| D1 | `links.to_note` 由 `NOT NULL` 改为可空，配 `broken=1` | 悬空链接没有目标笔记；原约束下"目标不存在"这件事无法登记，UI 就永远标不红 |
| D2 | 新增 `link_targets(from_block, target, to_block, kind)` 表 | 全量重建按路径顺序进行，指向"后面才入库的笔记"的链接在插入时查不到目标。改为两段式：插入期登记原始写法，`rebuild_links()` 统一解析 |
| D3 | 链接解析需保留 `#^b-xxx` 锚点（`to_block`） | 只解析到笔记级会让 AI 引用溯源退化成"指向整篇"，违背 G4 的可用性 |
| D4 | 自动块 ID 规则唯一化：`{note_id}#{ordinal}`，`blocks` 与 `chunks` 共用同一次前序遍历的结果 | 两处各自生成回退 ID 时，chunk 指向不存在的块，外键当场失败 |
| D5 | **列表不产生容器块**，条目直接是根层块 | `parent_id` 表达嵌套即可；引入容器块会让"条目 ID"被容器重复认领 |
| D6 | 引用/Callout 是容器块，正文由 children 承载，容器 `content` 留空 | 否则同一段文字在检索文本里出现两次 |
| D7 | Callout 标题取内部**第一行**，不等段落合并后再拆 | `> [!q] 标题` 与下一行 `> 正文` 会并成一个段落，标题会吃进正文 |
| D8 | `heading` 增加 ATX / setext 维度，setext 不参与规范化重建 | 重建会把 `文字
===` 变成 `# 文字`，那是改用户写法不是无损往返 |
| D9 | 参与规范化重建的类型是白名单：`paragraph / atx heading / todo / bullet / numbered / image / embed / file`，且要求源文本各行缩进齐整；否则回显 `raw` | **宁可少规整，也不吃语法**。G5 的"字节相等"因此定义为：未编辑的内容逐字节不变；编辑过的简单块按规范形重写 |
| D10 | `resolve()` 含 `..` 一律拒绝，不做事后规范化；前导 `/` 表示 Vault 根相对 | 拒绝比"悄悄纠正"安全：MCP 等外部入口传来的路径不该被猜 |
| D11 | 视图文件（`note_kind=view`）只登记 `notes` 行，不切块、不进 FTS/向量，且 `ai_private=1` | 兑现"视图不参与检索"的约定，否则视图会被自己的查询结果污染 |
| D12 | 回收站实际布局是 `.note/trash/<批次>/<原相对路径>`，批次名 `YYYYMMDD-HHMMSS-亚秒+序号` | 规格里的纯镜像存放会让"同一篇删两次"的 `rename` **静默覆盖**上一次的回收件。批次目录使每次删除互不重叠，清单靠扫目录得出、恢复目标从路径反推，仍然不存 DB 状态 |
| D13 | `before_delete` 快照尚未实现（`note_versions` 表已建、无人写入） | 删除的可恢复性由回收站里的**文件本身**保证，不依赖快照；`note_versions` 服务的是历史/撤销，与每日快照一起做，避免先写一个没有消费方的落盘格式 |
| D14 | 写命令命名与 [03] 的 IPC 表不完全同名：`save_note`/`read_raw` 而非 `note_write`/`note_read` | `read_note` 返回的是渲染用的块序列，编辑态要的是原文，两者必须分开——原名 `note_read` 无法区分。合并命名会逼前端在浏览时序列化整篇 Markdown |
| D15 | 改名会同时改文件名与 front-matter 的 `title` | 列表显示的是 `title`，只改文件名会让用户以为操作没生效。`id` 保持不变，所以按 id 认亲的链接图不受影响（有测试钉住） |
| D16 | `index_file` 重新索引同一篇时**原地更新 `notes` 行**，只在 id 也变了时才迁移入链后删旧行 | `links.to_note` 是 `ON DELETE CASCADE`：先删后插的写法会让"保存一篇被引用的笔记"静默清空所有指向它的反链（真机测出来过，引用方一个字都没改）。`INSERT OR REPLACE` 同样有此语义，已改 `ON CONFLICT DO UPDATE` |
| D17 | 移动/删除/恢复不再做全量 `rebuild_links`，改成按篇的"悬空→接回"：`break_incoming_links` 把入链置悬空，操作完 `resolve_broken_to` 再指回来 | 全量重解析的代价与库大小成正比（实测 2000 篇 156ms，是 8ms 预算的 20 倍），而它要修的东西只涉及与这篇相关的几条链接 |

附带一条实现事实：`status` 与 `origin` 都是**派生列**（分别由所在目录与 `props.source_url` 推出），与 §front-matter 不存 `status` 的裁决一致。
