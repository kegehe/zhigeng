# 02 · 数据模型与落盘格式

> 全项目唯一不可逆的决定。改错了，后面所有 AI 能力都建在错误的地基上。动工前先评审这一篇。

## 设计目标

同一份数据要同时是四种东西，不能为其中一种牺牲另一种：

1. **人可读的文档** —— 用户用 Obsidian / VSCode / git 直接打开编辑，不锁格式
2. **可寻址的知识单元** —— 每个块有稳定 ID，AI 的每条引用都能精确点回原文
3. **一张图** —— 笔记与块之间的链接是显式关系，供图谱与检索扩展使用
4. **RAG 语料** —— 可切片、可嵌入、可增量重建索引

## 四条数据层不变量

对应 [00-文档导航.md](./00-文档导航.md) 的 G1 / G5 在此层的细化。

| # | 不变量 | 违反后果 |
|---|---|---|
| I1 | Markdown 是用户笔记内容的唯一真相源，`index.db` 是纯派生物（例外见 §I1 例外清单） | 用户资产被自有格式绑架，本地优先名存实亡 |
| I2 | 删掉 `index.db` 必须能靠扫描 Vault 完整重建（设计上限 2 万篇 < 60s，不含嵌入；口径见 [03] §性能预算） | 索引腐烂后无法自救 |
| I3 | 方向只有 `md → db`。**永不**从 db 反向写 md（用户显式保存、接受建议、首次分配块 ID 除外） | 静默覆盖用户手改内容 |
| I4 | MD ↔ 编辑器模型字节级无损往返 | 用户其他编辑器里的内容被"保存"操作吃掉 |

### I1 例外清单（允许只存在于 `index.db` 的数据）

判据：**是不是用户亲手写下的内容**。以下不是，所以允许只在库里，删库后丢失属预期行为：

- 派生索引：分词结果、嵌入向量、切片边界、链接图的解析缓存
- AI 过程数据：`suggestions`、`ai_runs`、`jobs`、对话记录
- 性能缓存：缩略图、解析中间产物

**反例（必须能从 Vault 的 md 文件或目录结构中还原）**：笔记正文、标题、标签、属性、用户手写的链接、归档状态（= 所在目录）、视图定义（= `views/` 下的文件）。写代码时想往库里塞一张"只有 db 有"的用户数据表，必须先回来改这份清单。

## Vault 目录结构

用户选定一个文件夹作为 Vault（如 `D:\Notes`）。

```
<Vault>/
  inbox/                      # 未整理的快速捕获区，AI 整理任务的输入
    2026-09-22-standup.md
  notes/                      # 正式笔记，用户可自由建子目录，无限层级
    ai-native/
      主动层设计.md
      检索策略.md
    reading/
      2026-09-22-x 文章标题.md
  archive/                    # 归档（不是删除；移动即生效）
  views/                      # 动态视图 / 智能集合的定义文件（见 §视图与智能集合）
  attachments/                # 二进制资产，内容寻址命名，必须随 Vault 备份
    a3/a3f9c1e2....png
  .note/                      # 应用私有
    index.db                  # SQLite：FTS + 向量 + 图 + 建议箱 + 任务（可删可重建）
    trash/                    # 回收站：按原相对路径存放，清空即真删
    conflicts/                # 外部修改冲突时保留的磁盘版本，供用户手动比对
    versions/                 # 内容快照（gzip），撤销与历史依赖它
    config.toml               # 模型、自动化档位、快捷键、备份目录（删除后需重配，但不丢用户内容）
    tree.toml                 # 侧栏目录树的用户自定义顺序（删了退回默认序，但用户排的就没了）
    secrets.keyref            # 预留：只存"Windows 凭据管理器条目名"，不存 key 本身。2026-10-10 的 AI 档 0 没写它——条目名固定且可推导（`dev.note.service` + `ai`），再存一份就是第二真相；等支持一个库两把 Key 时才有记账的必要
    cache/                    # 缩略图、解析中间产物
    logs/                     # 按日滚动，保留 14 天
```

**`.note/` 内部两分**：`index.db` / `cache/` / `logs/` 是可再生层（删了自动重建）；`config.toml` / `tree.toml` / `secrets.keyref` / `trash/` / `conflicts/` / `versions/` 是需重配或不可丢层。**判据始终是同一条：删掉会不会让用户丢内容。** 备份指引里必须明确"Vault 整体复制即可完整迁移"。

#### 侧栏自定义顺序 `tree.toml`（M1）

用户把某一层拖成自己想要的次序，这份次序**既不是笔记内容也不是可再生索引**，所以它两头都不去：

- **不写进 Markdown 的 front-matter**：那等于让应用往用户手写的正文里塞自动生成的 rank 串，diff 与 `.note/versions/` 快照都会被搅脏，而且**目录没有 `.md` 可写**，顶层与目录就永远排不了。
- **不写进 `index.db`**：索引按 I1 是可丢弃重建的，重建一次就把用户排好的顺序抹了。

于是落在 `.note/tree.toml`，**一条 = 一个父目录的完整从上到下序列**（不是每篇一个数字）：

```toml
# 侧栏目录树的自定义顺序。每个 [[order]] 是一个父目录，names 从上到下。
# 没列进来的条目按默认规则排在列进来的之后；删掉某一段 = 这一层恢复默认。

[[order]]
parent = "notes"                       # 库根是空串 ""，其余正斜杠、无首尾斜杠
names = ["拖拽目标", "档 2 块渲染探针.md"]
```

八条口径：

| 口径 | 为什么 |
|---|---|
| 一次写**整层**的序列 | 落点本来就是同级整体算出来的。存稀疏 rank 要多处理"两个条目抢同一个数"，而这份文件是人能读、能手改的 |
| 保存按父目录**整条替换**，没点到的层原样留着 | 一次拖拽最多涉及两层（源层与目标层）。读—改—写这条纪律与 `config.toml` 一致 |
| 空序列 = 删掉那一条 | "这一层恢复默认"得有个说法，不能留一个空数组占位 |
| 坏档按"没排过序"处理，**读不出的 IO 错误照报** | 侧栏不该被一个坏 sidecar 拖起不来；但把只是暂时读不动的好档当空表，下一次保存就把它覆盖了 |
| **读回来的 `parent` 一律归一**（反斜杠换正斜杠、去首尾斜杠） | 前端拿这个字符串做**相等比较**（"这层排过序没有"、乐观合并），而排序那条路本来就归一。手改出一个 `notes/` 就会出现"屏幕上算同一层、写回时算两层"——拖走一篇时源层不被清理，同一层越攒越多条。归一必须在**边界**做完，不能指望调用方传得干净 |
| 名字与父路径里**不许有控制字符** | 手写序列化只转义 `" \ \n \t`，`\r`、ESC、NUL 是原样推进基础字符串的——那**整份文件**就是非法 TOML，下次读回来全体按坏档处理，所有层的顺序一起没。这些字符在 Windows 文件名里本就不允许，从界面走不进来；但 `parent`/`names` 是前端传上来的字符串，这道关口不该假设调用方诚实 |
| 坏档被覆盖前，**原文先存一份进 `.note/conflicts/`** | 坏档只可能是"人改出一个错字，其余层都是好的"（TOML 整篇读不回来）。按空表直接写回去=静默抹掉用户排好的顺序，违反 I1 那条分层判据；副本用时间戳后缀，连着坏两次也不互相覆盖 |
| **拖进目录**不把没排过序的目标层整层钉死 | 一次 `into` 落点只表达"这篇进那层"，不表达层内位置。把当时看到的整层序列写下去等于把那层变成自定义层：未列进来的排在列进来的**后面**，以后在那层新建的笔记会莫名沉底。所以只记"这篇排最前"，其余沿用默认规则。落到别层的**缝隙**上才写全序列——那是用户明说的位置 |

界面侧的优先级：**排过的条目优先于全部默认规则**（含"目录在笔记前面"与顶层三条 pinned），可以跨那道界；没排过的沿用默认规则跟在后面。默认序降级为"没拖过时长什么样"，而不是"不许拖成什么样"。

资产用 SHA-256 内容寻址命名 → 天然去重，同一张图被多处引用只存一份；原始文件名保留在 `attachments.orig_name`（派生，丢了可从 md 引用处重新解析）。

### 快照备份落在盘上长什么样（M1，docs/03 §备份）

备份目录在 **Vault 之外**（另一块盘 / NAS 挂载点），所以它是"库之外唯一一份用户内容副本"，格式必须自解释、能被资源管理器直接看懂：

```text
<备份目录>/
  <库名>-<库根路径hash前8>/        # 一个备份目录可以放多个库；hash 防同名库互相覆盖
    manifest.jsonl                 # 每行一份快照，按 taken_at 递增
    20260926-005225-795/           # 一份快照一个目录：本地时间到秒 + 毫秒
      notes/甲.md                  # 只放这份里**变化过**的文件（增量），原样不压缩
      attachments/ab/abc.png
```

每行 manifest 的字段：`id`（目录名）、`taken_at`（RFC3339）、`vault`（库根绝对路径）、`copied`（这份目录里实际写了哪些 rel）、`files`（**这份之后整个库的清单** rel → 内容 hash）。

三条不能改的规矩：

- **`files` 是全量而不是增量**。判断"某篇最后一次出现在哪份"要靠它；误删的文件在新快照的 `files` 里缺席，但实体仍躺在它被删之前的那份里——这就是验收 ⑨ 那条路。
- **先拷文件、后追加 manifest**。中途崩溃只留下一个没登记的目录，下次按上一份清单重算差异再拷一遍；反过来会留下指向半截文件的条目。
- **备份目录不许在 Vault 里面**（会在库里给自己做备份，体积按平方增长）。这条判据必须与 `Vault::open` 用**同一套路径归一化**（含剥掉 Windows 的 `\\?\` 前缀），否则比较两边一个带前缀一个不带，判据静默失效。

`.note/config.toml` 里的这一段是它的开关：

```toml
[backup]
dir = "E:\\笔记备份"      # 缺省 = 还没引导过，界面每次启动都提醒
disabled = true            # 显式"我不备份"，与上面那种情况必须可区分
```

恢复一篇文件走正常写盘路径（原子写），**被覆盖的那份先进 `.note/conflicts/`**——恢复本身是覆盖动作，被覆盖掉的那份也得留得下来。


### 扫描与排除规则

索引扫描器遍历 Vault 时的规则，写错一条就会出现"回收站里的笔记被 AI 引用"这类恶性 bug：

| 路径 | 是否索引 | 是否可被笔记链接到 |
|---|---|---|
| `notes/`、`inbox/`、`archive/`、`views/` | 建 `notes` 行（`archive/` 默认从检索结果排除，可显式包含）；**`views/` 只登记为 `note_kind='view'`，不进 `blocks`/`chunks`/FTS/向量**（见 §视图与智能集合） | 是 |
| `attachments/` | 只入 `attachments` 表，不产生 `notes`/`blocks` | 是 |
| `.note/` 及其全部子目录（含 `trash/`、`conflicts/`、`versions/`） | **一律不索引** | 否 |
| 任何以 `.` 开头的目录、`node_modules/` | 不索引 | 否 |
| 非 `.md` 的未知扩展名 | 不索引，但作为资产登记 | 是 |

**回收站的索引处理**：笔记移入 `.note/trash/` 时，同步删除其 `notes` 行（连带 `blocks`/`chunks` 级联与派生表清理），并在 `note_versions` 写一条 `reason='before_delete'` 快照；恢复时移回原路径重新解析。回收站列表本身由扫描 `.note/trash/` 目录得出，不存 DB 状态。

### 资产引用格式

**资产一律用 Vault 根相对的 Wikilink 引用**：`![[attachments/a3/a3f9c1e2....png]]`。

不用 `../attachments/xxx.png` 这类相对路径——笔记自身所在层级不同，相对前缀就不同（`notes/a/b.md` 需要 `../../`），手写和跨编辑器迁移都极易断链。前导的 `attachments/` 前缀配合内容寻址文件名，保证移动笔记不断链。解析器同时**兼容**用户从 Obsidian 带来的相对路径写法，并在解析后归一化。

**这一格式 2026-10-09 起真的在用了**（[03] §图片粘贴与单面图片块）：粘一张截图 → 字节按 sha256 落进
`attachments/<前两位>/<完整 sha>.<ext>`，正文里只多一行 `![[attachments/…]]`，`attachments` 表登记一行。
两条与本文档原来"只在纸上"的差别要说清：

- **扩展名由字节判，不由文件名判**。`orig_name` 那一列在粘贴这条路上是空的（剪贴板给的名字永远是
  `image.png`，没有信息量），它留给"拖文件进来"那一档填真名字；width/height 也仍为空，像素尺寸的真值
  要解码，与占位渲染一起在档 3 谈——**空着比写个估计诚实**。
- **界面只接管指向 `attachments/` 的引用**。裸文件名（`![[图.png]]`）与相对路径仍是"显示源文本"的
  不透明块，因为把它们画成图需要全库文件名解析（docs/05 记着没做）。**面板那一侧已经不等它**：
  2026-10-10 起资产链接的存在性按盘上判，三种写法都归一到同一个判据（见下）。

**资产链接的存在性按盘上判**（2026-10-10 接上，[03] §反链面板）：`links` 里指向资产的行
`to_note` 恒为 NULL，而"断没断"不再由"能不能解析成笔记"决定——判据是 `note_core::assets::exists`
这**唯一一份**函数，返回盘上真实存在的那个库内相对路径。为什么不能沿用"指不到笔记就是 broken"：
图就在 `attachments/` 里躺着，面板说"链空了"，这是屏幕上说的与落盘的不是同一句话。

- **三种写法收进同一个归一函数**：库内规范形（`attachments/ab/<sha>.png`）直接 stat；Obsidian 带来的
  相对路径（`../../attachments/x.png`）取"从 `attachments/` 开始的那一段"；裸文件名（`图.png`）先查
  `attachments` 表的同尾名，再走查 `attachments/` 目录。表里没有 ≠ 盘上没有（人名文件不登记，见下），
  所以那一步走查不能省。**越出库目录的写法一律判不存在**：`..` 与盘符在 `vault::resolve_in`
  那一条边界上就死，走查也只在 `attachments/` 之内。
- **索引期算一次写进 `links.broken`（只当排序用的缓存），读路径再算一次覆盖它**。理由很硬：
  外部删一个附件不会碰任何 `.md`，`watch::ignorable` 在攒批之前就把非 `.md` 挡了，事件根本到不了
  索引层——只有现算才追得上盘上。真机三态验过：图在 → "附件在库内"；把图挪走（不改任何 `.md`、
  不重索引）→ 面板改口"文件丢了"；放回来 → 又回到"附件在库内"。
- **`[[notes/乙.md]]` 这类"写法里带点的笔记引用"不按盘上判**。`link_kind` 只看有没有 `.`，
  所以它也被标成 asset，但它的真值是笔记表里那一篇；`LinkRow` 因此带一位 `toNote`，
  面板靠它决定"这一行能不能点开成一篇"，而不是在界面上特判前缀。
- **`attachments` 表的重建路径就在这条链路上**：`Index::rebuild_all` 扫 `attachments/` 目录，
  按**文件名声明**的 sha 登记（内容寻址的名字里就写着 sha，不需要重读字节），`first_seen_at` 取 mtime。
  两条边界要说白：文件名不是 64 位小写十六进制的（手工拖进来的人名文件）**不登记**——给它编一个
  主键比少一行更坏；登记不校验字节与名字是否相符，那是另一条命令（`note verify-assets`，还没做）的活。
  重建时先把**盘上已经不存在的那些行**摘掉，仍存在的行原样保留（`orig_name` 记的是"第一次粘进来时
  它叫什么"，重建不该抹掉它）。

## Markdown 扩展约定

基底是 **CommonMark + GFM**，只增加四处约定：块 ID、Wikilink 链接、Callout、front-matter 扩展字段。除此之外**不许发明私有语法**——每加一条私有语法，就多一分与其他编辑器互不兼容的债。

### 块 ID（Obsidian 兼容语法）

块 ID 追加在块末行尾部：` ^b-<10 位小写字母数字>`（详细选型论证见 [adr/ADR-002-块ID语法.md](./adr/ADR-002-块ID语法.md)）。

- 选 `^b-xxx` 而非 `{#xxx}`：**双向兼容**是本地优先的命脉。用户在 Obsidian 写的 `[[笔记#^b-xxx]]` 我们直接认，反之我们的链接他在 Obsidian 里能跳。
- 代价：不支持块 ID 的渲染器（如 GitHub）会把尾部 `^b-xxx` 当正文显示。可接受，且导出 HTML 时统一剥离。
- 代码块、表格、Callout 等无法在末行内追加时，ID 独占一行写在块之后。
- 无 ID 的块（用户手写、导入）在首次索引时自动分配 ID 并回写一次。**回写前必须弹窗告知**，因为这是"应用改动用户文件"。
- ID 一经分配永不复用、永不因移动或编辑而改变。删除块则 ID 作废，指向它的链接变悬空链接（UI 标红，不自动删）。
- **冲突规则**：两个文件带同一 `id`（用户直接复制文件导致）时，路径字典序靠前者保留 ID，后者重新分配并在建议箱提示"检测到复制的笔记"。

### 链接

| 语法 | 含义 |
|---|---|
| `[[笔记名]]` 或 `[[notes/子路径/笔记名]]` | 笔记级引用 |
| `[[笔记名#^b-xxxxxxxxxx]]` | 块级引用（AI 溯源用这个） |
| `[[笔记名#一级标题]]` | 标题锚点 |
| `![[笔记名]]` | 嵌入，渲染时内联展开 |
| `[[笔记名` + 竖线 + `别名]]` | 带显示别名（Obsidian 竖线语法） |

相对路径链接 `[文本](./a.md)` 与外链一并解析入图。

### 块类型（v1 共 15 种）

全部必须能用 Markdown 无损表达，这是"不锁格式"的硬约束（G1）。

| type | Markdown 表示 |
|---|---|
| `paragraph` | 普通段落 |
| `heading` | `#` 至 `######` |
| `todo` | 减号加空格方括号，`- [ ]` / `- [x]`；到期与完成时间见 §待办的到期约定 |
| `bullet` | 无序列表项，嵌套层级由 `parent_id` 表达 |
| `numbered` | 有序列表项，嵌套同上 |
| `quote` | 引用块 |
| `callout` | Obsidian 风格 `> [!note]` |
| `toggle` | 折叠式 Callout（`> [!note]- ` 形式） |
| `code` | 三反引号围栏 + 语言标识 |
| `table` | GFM 表格 |
| `math` | `$$` 块级公式 |
| `image` | `![[attachments/a3/xxxx.png]]`（见 §资产引用格式） |
| `file` | 指向非图片资产的链接 |
| `embed` | `![[...]]` |
| `divider` | 独占一行的 `---` |

**`---` 的解析优先级**（三处冲突必须固定规则，否则往返有歧义）：文件第一行的 `---` 是 front-matter 起始边界；紧随段落之后的 `---` 按 GFM 规则优先解析为 setext H2 下划线（**保持 GFM 行为，不改**）；其余独立成段且前后为空行的 `---` 解析为 `divider`。编辑器写入分隔线时总是补空行。

白板、内嵌数据库渲染、批注层高亮 → v1 明确不支持，因为它们无法无损落成 Markdown。

### 兜底类型 `raw`（第 16 种，仅内部使用）

超出上述 15 种、或解析器不认识的块（其他编辑器带来的私有语法、HTML 片段、未知指令），一律解析为 `raw` 类型：**原样保存源文本，UI 只读渲染为等宽灰底代码块，编辑器不解析其内部结构**。

`raw` 是 G5（无损往返）的最后防线——丢内容永远比丢类型严重。配套两条硬规则：

1. `raw` 块**不进 AI 上下文**（语法未知的内容容易带隐私标记或指令注入文本），且计入索引健康报告的"未识别块数"，非零时在设置页可见
2. AI **不得对 `raw` 块提 `restructure`/`split` 建议**（不认识就无法保证改写正确）

### 视图与智能集合（`views/`）

"把一次语义查询存成动态目录"是用户创造的内容，删库后必须能还原，所以**不能只存 DB**，也不能新增私有格式——复用笔记机制：

```md
---
id: n-v12mk8pq
title: 待整理的 AI 原生想法
view:
  kind: smart            # smart（语义/条件查询）| table | board | calendar
  query: "AI 原生"
  filter:
    tags: [ai-native]
    status: inbox
  sort: created desc
  limit: 200
---
```

`views/` 下的文件有 `view` 字段即被识别为视图而非普通笔记：不出现在正文编辑器里，渲染为动态列表。查询结果每次实时算，**绝不缓存成"看起来是数据"的表**，所以它对 I1 完全无负担。

三条配套规则，避免它变成"其实我们支持了内嵌数据库"：

- 视图文件**不参与检索、不进 AI 上下文**（它是查询定义，不是知识内容；否则一个"待补清单"视图会反复污染 gap_scan 的结果）
- v1 **不支持在正文里 `![[views/xxx]]` 嵌入视图**。这与"不支持内嵌数据库渲染"是同一条决心的两面：视图只在独立页面与侧栏打开
- 视图渲染时读取的是实时查询，所以视图本身永不需要"保存结果"，也不产生 diff 冲突普通静态视图（按标签/属性筛选的表格、看板、日历）同样落在这里。

### front-matter（YAML）

只放用户拥有且看得懂的元数据。**派生物（嵌入向量、分词、摘要缓存）一律不进 front-matter**，避免污染文件和 diff。

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | `n-` + 8 位；文件改名/移动都不变，用于认亲 |
| `title` | 否 | 缺省时取首个 H1，再缺省取文件名 |
| `tags` | 否 | 扁平标签数组 |
| `created` | 是 | 首次写下时间，AI 判断"我什么时候想过这个"的依据 |
| `props` | 否 | 任意键值，属性/看板/日历视图的数据源。保留键见下表 |
| `ai.private` | 否 | `true` 时该笔记任何块不得进入 AI 上下文 |
| `ai.no_ai` | 否 | 连摘要、打标都不做（比 private 更严格） |

**`props` 保留键**（有语义，UI 会区别对待；其余键是用户自定义）：

| 保留键 | 含义 |
|---|---|
| `as_of` | 该笔记内容的"截至何时我认为为真"。AI 判断信息陈旧、`resurface` 决定"三个月前想过"都读它；缺省回落 `created` |
| `source_url` / `fetched_at` | 网页剪藏来源，写入即代表**内容来自外部**（影响 `origin` 与注入防护，见下） |
| `due` | 见 §待办的到期约定 |

### 待办的到期约定

`gap_scan` 要判断"待办已过期"，但 CommonMark/GFM 的 `- [ ]` 里没有日期位置。约定用社区已有的 **`key:: value` 行内字段**（Obsidian Tasks / Dataview 的既有语法，不是我们发明的私有语法）：

```md
- [ ] 把主动层的触发点定下来 due:: 2026-09-28 ^b-t6j9l2n5ey
```

- 解析进 `blocks.props_json`（`{"due":"2026-09-28"}`），渲染时从可见文本里剥离并显示成日期胶囊
- **只识别 `due::` 与 `done::` 两个键**，其余 `key::` 一律当普通文本，不做任何猜测——社区约定没有注册表，猜错就是吃掉用户内容
- 未知键原样保留，序列化时按原文写回（G5）

### 内容来源 `origin`

派生列，不落 front-matter：有 `props.source_url` 或来自导入 → `clipped` / `imported`，否则 `human`。

它存在的唯一理由是 [04] §全局契约的注入防护需要能**在 SQL 层**区分"用户自己写的"和"从网上扒来的"，而不是靠模型自觉。

**没有 `status` 字段。** 状态权威是**文件所在目录**：`inbox/` → inbox，`archive/` → archived，其余 → active。把状态同时写进 front-matter 和目录会造成双真相，必然漂移。DB 的 `notes.status` 是解析时推导出的缓存列。

**没有 `updated` 字段。** 每次保存都改 front-matter 会造成 git diff 噪音；更新时间由文件 mtime + DB 记录承担。

## 索引层 Schema（SQLite）

`<Vault>/.note/index.db`。WAL 模式，`foreign_keys=ON`。

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- 必存：schema_version, md_format_version, vault_id, jieba_dict_version,
--       last_full_reindex_at, active_embedding_model

CREATE TABLE notes (
  id           TEXT PRIMARY KEY,          -- front-matter id
  path         TEXT NOT NULL UNIQUE,      -- 相对 Vault，正斜杠
  title        TEXT NOT NULL,
  note_kind    TEXT NOT NULL DEFAULT 'note',  -- note | view（views/ 下的动态视图定义）
  status       TEXT NOT NULL DEFAULT 'active',  -- 派生自所在目录，不写回 md
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,             -- 来自 mtime
  content_hash TEXT NOT NULL,             -- 整篇 sha256，判增量与陈旧
  ai_private   INTEGER NOT NULL DEFAULT 0,
  no_ai        INTEGER NOT NULL DEFAULT 0,
  origin       TEXT NOT NULL DEFAULT 'human',  -- human|clipped|imported，派生；AI 注入防护靠它过滤
  -- 为未来多端同步预留，第一版不写值；加列比改表便宜
  rev          INTEGER NOT NULL DEFAULT 0,
  device_id    TEXT
);

CREATE TABLE blocks (
  id            TEXT PRIMARY KEY,          -- b-xxxxxxxxxx
  note_id       TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  parent_id     TEXT REFERENCES blocks(id) ON DELETE CASCADE,  -- 列表嵌套
  ordinal       INTEGER NOT NULL,          -- 文档顺序
  type          TEXT NOT NULL,
  heading_level INTEGER,
  text          TEXT NOT NULL,             -- 剥离语法后的纯文本（可为空串）
  markdown      TEXT NOT NULL,             -- 原始片段，含块 ID 标记
  line_start    INTEGER NOT NULL,
  line_end      INTEGER NOT NULL,
  props_json    TEXT,                      -- 类型专有属性：语言/勾选态/URL/alt
  UNIQUE (note_id, ordinal)
);

-- RAG 检索单元：1..N 个连续块组装成 200–800 token。
-- 单块太小缺上下文，整篇太大浪费预算。
CREATE TABLE chunks (
  id          INTEGER PRIMARY KEY,
  note_id     TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  start_block TEXT NOT NULL REFERENCES blocks(id) ON DELETE CASCADE,
  end_block   TEXT NOT NULL REFERENCES blocks(id) ON DELETE CASCADE,
  header_path TEXT,                        -- "主动层设计 > 触发点"，作上下文前缀
  token_count INTEGER NOT NULL,
  text        TEXT NOT NULL,               -- 含前缀的实际嵌入文本
  source_hash TEXT NOT NULL                -- 变了就重嵌
);

-- 全文检索：FTS5 的 unicode61 不分中文词，必须由 jieba-rs 预分词后写入 seg 列。
-- 刻意用独立 FTS 表（自带内容）而非 external-content 表：重解析一篇笔记时
-- 只需 DELETE + INSERT，不必维护触发器与影子表，少一类"索引和主表不一致"的 bug。
-- rowid 显式对齐 blocks.rowid / chunks.rowid。
CREATE VIRTUAL TABLE blocks_fts USING fts5(
  seg, tokenize="unicode61 remove_diacritics 2"
);
CREATE VIRTUAL TABLE chunks_fts USING fts5(
  seg, tokenize="unicode61 remove_diacritics 2"
);

-- 向量：每个嵌入模型一张 virtual table，换模型 = 建新表 + 全量重嵌。
-- 语法为 vec0（旧文档里的 vec_embeddings 已废弃，见 ADR-003）：
-- CREATE VIRTUAL TABLE vec_bge_m3 USING vec0(embedding float[1024]);
-- vec 表 rowid 与 chunks.id 对齐；向量以小端 f32 拼成的 BLOB 传入。
-- 扩展经 sqlite3_auto_extension 静态注册，不分发 .dll，且全仓库禁止 load_extension。
--
-- 2026-10-10 真装了一版之后，四条只在实现时才看得见的细节（`note_core::embed`）：
--   ① **表名带模型名的 hash 后缀**（`vec_fake_emb_760f14`）。只把非 `[a-z0-9]` 换成 `_`
--      的话，`gpt-4` 与 `gpt_4` 会归一成同一个串撞进同一张表——两种模型的向量混在一起，
--      KNN 回来的距离不再有意义，而且不报错。
--   ② **`distance_metric=cosine`**：与向量长度无关，换模型时分数分布不会整体漂移
--      （阈值是评测集标出来的，漂移等于阈值作废）。
--   ③ **重嵌是"先删后插"**，不是 `INSERT OR REPLACE`：vec0 是虚拟表，没实现 REPLACE 那条
--      路径，重嵌同一个切片会直接 `UNIQUE constraint failed on vec_… primary key`。
--   ④ **隐私过滤在嵌之前，不在召回之时**：`ai_private` / `no_ai` 的笔记与 `views/` 根本不进
--      待嵌清单。docs/04 那条硬门说的是"别进 AI 上下文"，而把字节发给云端 API 比进上下文
--      更不可逆——只在召回时过滤，等于"已经发出去了，只是不显示给你看"。
--      取证：假端点把收到的请求体落了盘，公开两篇的切片在里面，私密那篇的银行卡号不在。
CREATE TABLE embeddings (
  chunk_id    INTEGER NOT NULL REFERENCES chunks(id) ON DELETE CASCADE,
  model       TEXT NOT NULL,               -- 'bge-m3@1'
  dims        INTEGER NOT NULL,
  embedded_at TEXT NOT NULL,
  PRIMARY KEY (chunk_id, model)
);

-- 标签/属性：纯派生自 md，只存已落盘的。AI 建议的标签在未确认前留在 suggestions，
-- 不写这里（否则删库即丢，且违反 I1）
CREATE TABLE tags (
  note_id TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  tag     TEXT NOT NULL,
  PRIMARY KEY (note_id, tag)
);
CREATE TABLE props (
  note_id TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  key     TEXT NOT NULL,
  value_text TEXT, value_num REAL, value_date TEXT, value_json TEXT,
  PRIMARY KEY (note_id, key)
);

-- 图。同样只存 md 里真实存在的链接；AI 提议的链接在 suggestions 里，
-- 确认后写进 md，于是自然出现在这张表。provenance 用于区分人写与导入。
CREATE TABLE links (
  id         INTEGER PRIMARY KEY,
  from_block TEXT NOT NULL REFERENCES blocks(id) ON DELETE CASCADE,
  -- 悬空链接没有目标笔记，必须可为空，否则 UI 标不红、反链面板也说不出"链到了谁"
  to_note    TEXT REFERENCES notes(id) ON DELETE CASCADE,
  to_block   TEXT REFERENCES blocks(id) ON DELETE SET NULL,
  target     TEXT NOT NULL DEFAULT '',     -- 用户写下的原始写法（schema v3）。悬空时仅剩的信息
  kind       TEXT NOT NULL,                -- ref | embed | asset（父子页面关系由目录派生，不入此表）
  provenance TEXT NOT NULL DEFAULT 'human',-- human | imported
  broken     INTEGER NOT NULL DEFAULT 0,   -- 悬空链接：目标不存在，UI 标红
  created_at INTEGER NOT NULL DEFAULT 0
);

-- G3 红线落地处：AI 的一切写意图先落这张表，accept 才动 md
CREATE TABLE suggestions (
  id         TEXT PRIMARY KEY,
  kind       TEXT NOT NULL,   -- 枚举见 04 文档 §3，两文件必须一致
  note_id    TEXT REFERENCES notes(id) ON DELETE CASCADE,
  block_id   TEXT REFERENCES blocks(id) ON DELETE CASCADE,
  payload_json TEXT NOT NULL, -- 文件级操作列表 + expect_hash，格式见 [04] §补丁格式
  basis_json   TEXT,          -- 依据哪些块，供 UI 展示"为什么这么建议"
  status     TEXT NOT NULL DEFAULT 'pending',  -- pending|accepted|rejected|expired|applied|undone
  model      TEXT, created_at TEXT NOT NULL, decided_at TEXT
);

CREATE TABLE ai_runs (
  id TEXT PRIMARY KEY, task TEXT NOT NULL, model TEXT NOT NULL,
  trigger TEXT NOT NULL,             -- manual|job|edit|capture
  in_tokens INTEGER, out_tokens INTEGER, cost_usd REAL,
  ok INTEGER NOT NULL, error TEXT, duration_ms INTEGER,
  cited_blocks_json TEXT,            -- 审计：这次回答用了哪些块
  created_at TEXT NOT NULL
);

CREATE TABLE conversations (
  id TEXT PRIMARY KEY, title TEXT, created_at TEXT NOT NULL, pinned INTEGER DEFAULT 0
);
CREATE TABLE messages (
  id INTEGER PRIMARY KEY,
  conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  role TEXT NOT NULL, content TEXT NOT NULL,
  citations_json TEXT,               -- [{note_id,block_id,quote}]
  created_at TEXT NOT NULL
);

-- 主动层的本地 cron
CREATE TABLE jobs (
  id TEXT PRIMARY KEY, kind TEXT NOT NULL,   -- tidy_inbox|weekly_review|gap_scan|...
  cron TEXT, next_run_at TEXT, last_run_at TEXT,
  status TEXT NOT NULL DEFAULT 'ready',      -- ready|running|failed|disabled
  attempts INTEGER DEFAULT 0, payload_json TEXT, result_json TEXT
);

CREATE TABLE attachments (
  sha256 TEXT PRIMARY KEY, path TEXT NOT NULL, orig_name TEXT, mime TEXT NOT NULL,
  size INTEGER NOT NULL, width INTEGER, height INTEGER,
  ocr_text TEXT, first_seen_at TEXT NOT NULL
);

-- 版本历史：内容 hash 去重 + 30 分钟合并窗口，避免每敲一键一条。
-- 例外：reason='ai_applied' 与 'before_delete' 的快照不参与合并、不被清理策略丢弃，
--       它们是建议撤销（04 §建议的生命周期）与回收站恢复的唯一落点。
-- 快照落 .note/versions/（不可再生，撤销依赖它）
-- 钥匙是 path 而不是 note_id，且**不挂外键**：笔记进回收站时 notes 行会消失，
-- 而版本必须活得比笔记久（撤销与恢复都要它）。挂 ON DELETE CASCADE 的话，
-- 删笔记就把版本一起带走了——而那正是唯一要用的落点。
CREATE TABLE note_versions (
  id INTEGER PRIMARY KEY, path TEXT NOT NULL,
  note_id TEXT NOT NULL DEFAULT '',
  content_hash TEXT NOT NULL, blob_path TEXT NOT NULL,
  reason TEXT, created_at INTEGER NOT NULL,    -- reason: manual|ai_applied|auto|before_delete
  UNIQUE (path, content_hash)
);
```

### 时间列的类型：以代码为准（2026-10-10 核对）

上面那段 DDL 除了 `notes.created_at`（来自 front-matter，是人看得懂的文本）与 `note_versions.created_at`
（2026-10-24 已按实现改成 INTEGER）以外都还写着 `TEXT`，
而实现里派生表与审计表的时间一律是 **INTEGER epoch 毫秒**（`suggestions` / `ai_runs` /
`conversations` / `messages` / `jobs` / `attachments` / `note_versions`）。这一处不改代码改文档的理由：
索引库是**可重建的缓存**，读的人按 `ORDER BY created_at DESC` 拿到的必须是数值序——TEXT 上那是字典序，
十位数的毫秒时间戳恰好也是单调的，所以它"看起来一直是对的"，直到 2286 年或者有人写了非纯数字的时间。
**别照着这段 DDL 去理解盘上的库**，`crates/note-core/src/schema.rs` 才是跑着的那一份。

### `ai_runs` 从 2026-10-10（M2 档 2a）起真的有写入了

每次问答落一行（含**没被采纳**的那些——审计页只列成功记录就不是审计）：

| 列 | 这一档写什么 |
|---|---|
| `task` / `trigger` | 恒为 `'ask'` / `'user'`（界面发起；CLI 的 `note ai ask` 也算） |
| `ok` | `= 答案被采纳`。零候选拒答、模型自称依据不足、两次都越界 → 记 **0**，`error` 写 `依据不足或降级` |
| `in_tokens` / `out_tokens` | 两趟（违规后重生成）**累加进同一行**；提供方没回 `usage` 时记 0 而不是猜 |
| `cost_usd` | 留 NULL——还没做价格表，空着比填一个编出来的数诚实 |
| `duration_ms` | 从第一次发问到定稿的墙钟时间，含重试那一趟 |
| `cited_blocks_json` | `{"cited":[块ID…],"candidates":N,"retried":bool,"semantic":bool}`。`cited` 是真块 ID（界面上要能点回去），后面三项是审计页要能看出"这条是第二次才过的 / 这一趟语义路开着"的来源 |

`conversations` / `messages` / `suggestions` / `jobs` 仍是**建好但零写入**：对话持久化与流式问答是下一档，
建议箱是 M3。

### 派生表的手工清理（易错点）

FTS5 与 sqlite-vec 的 virtual table **不参与外键级联**。重解析或删除一篇笔记时，`blocks`/`chunks` 会随 `ON DELETE CASCADE` 消失，但 `blocks_fts`、`chunks_fts`、`vec_*` 里的行会残留成孤儿，导致检索命中已不存在的内容。

因此**每次笔记级重建必须按顺序显式执行**：

1. 先查出该笔记所有 `blocks.rowid` / `chunks.id`（此时主表还在）
2. 用上一步的 id 删 `vec_*` 行 → 删 `blocks_fts` / `chunks_fts` 行（`WHERE rowid = ?`）
3. 删 `chunks` / `blocks`（外键级联）→ 重新插入 → 重建 fts 与 vec 行

**步骤 1 不能省**：`blocks` 的 rowid 是隐式行号，一旦先删了主表就再也找不到对应的 fts 行，孤儿必留。全量重建则直接 `DROP` 后重建 fts 与 vec 表，比逐行删快一个数量级。这条要在 `index` 模块用单测覆盖：删一篇笔记后跑一次全库检索，命中数必须归零。

## 写入与外部修改

**保存路径**：写临时文件 → `FlushFileBuffers` → `ReplaceFile`（原子改名）→ 重算 hash → 增量重建该笔记索引 → 写 `note_versions` 快照。崩溃不产生半截文件。

**快照写的是前像**（那次操作**之前**盘上的内容）：撤销要的是"回到没改之前"，存后像就等于存了"再往前一版"，中间那一步——正是用户要撤的那一步——永远撤不回来。三条落快照的路：保存（`manual`）、从备份快照恢复（`manual`）、移进回收站（`before_delete`）。30 分钟合并窗口只作用于 `manual`（连续编辑不该在历史里留一串），`ai_applied` 与 `before_delete` **不合并、不清理**——它们是撤销与恢复的落点。**快照分两半落**：同步那一半只读盘、只排队，blob 与行由后台那一半落（D33）。

**外部修改**（用户在 Obsidian/VSCode 里改了文件，`notify` 监听到）：

| 情形 | 处理 |
|---|---|
| 本地无未保存改动 | 直接重解析该文件，UI 刷新 |
| 有未保存改动，且磁盘 hash ≠ 我们上次写入的 hash | 冲突：保留双方，磁盘版本落 `.note/conflicts/` 并提示，**绝不静默覆盖** |
| 仅 mtime 变化、hash 相同 | 忽略（编辑器自动保存噪音） |

改名与移动按 `id` 认亲，不按路径，避免链接图断裂。找不到 `id` 时退化为按"路径 + 内容 hash 相似度"匹配。

**删除**：移动到 `.note/trash/<原相对路径>`，恢复即移回。清空回收站才真正删文件。状态存于目录本身而非 DB 列，同样是为了不违反 I1。

## 版本与迁移

- `schema_version`（整型）：DB 结构版本。破坏性变更走"删库重建"——索引是派生物，**不写迁移脚本，只写重建器**。
- `md_format_version`：块 ID / front-matter 约定版本。**这个必须写迁移脚本**，因为它长在用户资产里。v1 → v2 需 dry-run + 全量备份后再改。
- 重建器与增量解析器必须共用同一份 `md-kernel` 代码路径（`reindex = parse(all files)`），杜绝"重建出的索引和增量更新的不一致"。
- 遇到无法解析的块：降级为 `raw` 类型原样保留，规则见 §兜底类型 `raw`。丢内容永远比丢类型严重。

| D29 | 不透明块的**显示形是源文本的派生投影**：没有光标的块画成渲染后的样子（表格成网格、引用去 `>` 前缀、代码去围栏、锚点不显示），光标进来退回源文本形；显示形**不参与序列化**，也不写回任何字节 | I1 说 md 是唯一真相源，I4 说往返必须无损——这两条都不反对"多画一层"，反对的是"为多画一层改字节"。所以判据是同一条：**渲染画错了最坏是看着不对，改源码就能改回来；落盘那条路一个字都不许被它碰过**。代价是同一块有两副面孔，用户点进去会看到 `| 列 |`；不这么做的替代方案是给表格/代码做结构化编辑面板，那要求序列化器先产得出这些语法（D27 判死过一次的坑）。**画不来的类型（HTML、未识别语法、带子项的列表项）必须继续显示源文本**——把内容收进一个空宿主里等于在界面上吃掉这一块，那是换形式的 I4 违反。Callout 的折叠态只活在 DOM 上，不写回源文本的 `-`：界面上的状态与文件里的字节各活各的，就得重开 I1 |
| D30 | 反链面板要显示"链到了不存在的 `[[某写法]]`"，所以 `links` 补一列 `target`（schema v2 → v3，见 §索引层 Schema）。迁移按**先换形状、再算内容**：两档要 DROP 的表一次 drop 完 → 跑一遍 `SCHEMA` → 需要重灌的暂存表重灌 → 最后 `rebuild_links` 一次 | 这条迁移在真机上炸过一次，两个根因都值得写下来：① 原先每档各自"drop / 建 / 算"，v1 库走第一档时 `links` 还是旧形状，`rebuild_links` 插 `target` 列就报 `table links has no column named target`，**整个库打不开**（界面退回"选一个目录"，用户看到的是"我的笔记不见了"）；② 迁移跑完只 `pragma_update(user_version, 旧值)`，`meta` 里那条 `schema_version` 压根没更新，于是**每次开库都重跑一遍迁移**（对大库就是重扫全库的块重算链接图）——真库一直停在 v1 就是它造成的。教训：`links` 这类**纯派生表**的迁移只能是"删掉重算"，而"算"必须放在所有形状都就位之后；版本号是迁移的一部分，不是收尾装饰 |
| D31 | **表格从"只渲染、编辑走源文本"里例外出来**：接管得过来的 GFM 表建成 `mdTable` 节点树，格子里直接打字、`Tab` 跳格、末格 `Tab` 加一行、工具栏加行加列。接管判据保守——列数不齐 / 带 `^b-` 锚点 / 行首缩进 / 中间空行一律不接管，继续是不透明块。这条收窄了 D27 的适用范围（D27 说"表格是不透明块所以菜单不给它"，那句仍然成立：**表格不给类型切换**；变的是序列化器现在产得出 GFM 表了） | 用户的原话是"为什么我创建的表格打开还是 markdown"。不是渲染坏了，是规则本身对表格不成立：两副面孔要"点进去改源码"，而填格子就必须待在格子里，于是永远看到 `| 列 |`。代价是这条路第一次让"改一个格子"重写整块字节，所以判据必须是**能不能拼回去**而不是能不能解析：GFM 允许列数不齐（缺的列补空、多的列截断），而"补/截"就是替用户改内容。锚点那条同因——`| 1 | 2 | ^b-xxx` 会被读成第 3 格，独占一行的那种内核又不认成 id（另记一条待查），两种都拼不回去。而这条判据本来也用不到表格身上：格子里的 Enter 被 `TableKeys` 接管成跳格，表格拆不出"相邻两块同源"这种产物。没动的表仍按 `raw` 逐字节回写，所以现有 03 / 06 夹具的字节断言一个字都没改。**产出的格子里不许有换行**：`写格()` 把 `\n` 连同邻近空白折成一个空格——GFM 的格子里换行就是行结束，漏一个进去整块再也拼不成表，那是形状破坏（比"分隔行被规整"严重一档），所以拦在写盘前的最后一道关口，而不是指望输入层堵住（真机测下来 Chromium 的输入层确实会顺手把换行收掉，但那不是契约，也不归我们控制）。**粘贴进来的表走同一道判据**：空段落里粘 Markdown 源文本或电子表格的 TSV 才落成网格，判据就是 `parseTable` 那一条加"TSV 每行列数必须相同、至少两列两行"，**CSV 不认**（逗号在正文里太常见，把一句话切成三列是拿用户的内容赌概率）；认不准就按纯文本粘，宁可让用户看到 `| 列 |` 也不猜。**表格的编辑动作到此闭环**：加行 / 删行 / 加列 / 删列 / 本列靠左·居中·靠右·取消对齐，全部只产 GFM 已有的语法——删行不许删表头行（GFM 的表必须有表头），删列不许删掉最后一列（空表不是表），对齐改的是**分隔行**（`:---` / `---:` / `:---:`）而不是样式。**编辑器里表格后面永远跟一个空段落**（插入 / `/` 替换 / 粘贴三条路都自带，最后一行按 `↓` 也会现补一个）：以表格结尾的文档放不出光标，用户就写不了表格下面的东西；而这个空段落按"重新产出后是空白的块不落任何字节"那条**不写进文件**，所以盘上仍然只有那张表 |

| D32 | `note_versions` **换钥匙**：`note_id` → `path`，且**去掉外键**（schema v3 → v4）。迁移**保行**，不按"删库重建"那套 | 原来的 `note_id REFERENCES notes(id) ON DELETE CASCADE` 有一个致命后果：笔记进回收站 → `notes` 行被删 → **版本跟着级联消失**——而那正是撤销与恢复唯一要用的落点。改成 `path` 之后版本活得比笔记久（删了、进回收站了都还在）。这一档也不能走"破坏性变更删库重建"：索引是派生物所以能重算，**版本不是**——盘上早就没有那一版了，重算不回来。所以迁移是"旧表改名保住 → 跑 `SCHEMA` 建出新形状 → 搬行 → 删旧表"，旧行的 `path` 从 `notes` 表反查（查不到就留空串）。有专门一条用例钉住它（`老库的版本表换钥匙但不丢行`） |
| D33 | 版本快照的**落盘分两半**：同步那一半只读盘、只把前像排进内存队列；blob 与行由后台那一半落 | 往 SQLite 写一行要跟后台那条连接抢写锁，而主锁被后台事务占住时前台任何一条命令都得排队——那是 3.26 秒那次事故的形状，不能在写路径上再买一次。读盘不花钱：冲突判定本来就要读同一份（`读前像` 一次读干两件事）。队列挂在 `Index` 上、`fork()` 复制同一个 `Arc`，所以主连接排进去的东西后台那条连接看得见。爆队时丢最老的一条（丢的是"历史里的一版"，不是笔记本身） |
| D34 | **目录成为一等公民**（2026-10-24，档 A）：新增 `dir_list` / `dir_create` / `dir_rename` / `dir_delete`，`note_create` 多收 `parent`。树仍由前端从 `rel` 拼，但**空目录只能靠 `dir_list` 才看得见**——它给的是"盘上有哪些目录"的清单，不是另一棵树的形状 | 空目录不会出现在任何一篇的 `rel` 里，光拼树永远看不见刚建出来的文件夹；但让后端返回一棵树又多出一处会与盘上事实分叉的结构。所以两边分工：**形状在前端（层级、排序、折叠），事实在后端（存在哪些目录）**，`buildTree(行, 顺序, 目录)` 把两者叠起来。判据只有一份 `is_tree_dir`：`views/`、`attachments/`、`.note/` 这类应用私有与有别的语义的树、点开头的目录、`node_modules` / `target` 都不在笔记树里，列、建、改名、删、以及"在哪建笔记"全部问它。**档 A 的边界是物理空目录**：改名/删除只做空目录（`read_dir().next()` 判），非空目录要搬整棵子树 + 批量重索引 + 链接指向（档 B），所以界面不给入口、服务端也拒；顶层 `notes` / `inbox` / `archive` 是保留名，可以往里建东西，但不能改名/删除。目录名 **只拒不改**（`check_dir_name`）：空、`.`/`..`、点开头、控制字符、Windows 保留字符与保留名、结尾的点、超 80 字符一律报错，不替用户修剪。**目录改名/删除时 `tree.toml` 跟着搬**：`rename_path` / `remove_path` 重写父层里的名字，并给随目录消失的旧层追加一条空序列墓碑——`tree_order::save` 是按父目录整条替换的，不显式删掉那条，旧键会永远留在文件里（这次实现时真踩到，用例钉住了）。**复查补齐（2026-10-24）**：① **判据大小写不敏感**（ASCII）——NTFS/APFS 上 `NOTES` 与 `notes` 是同一个物理目录，精确比较会让 `NOTES` 既不算保留名、又照样被 `resolve` 落到保留目录上；现在保留名、排除名（`node_modules` / `target`）、`attachments/` / `views/` 首段一律按 `eq_ignore_ascii_case` 判，`list_dirs` 也按同一个判据剪枝。② **目录名首尾空白改为拒绝**而不是 `trim()` 后悄悄改：文档一直写"只拒不改"，代码却在修剪——用户输入 `" 项目 "` 时建出来的目录名不是他打的那个。③ **只改大小写的改名放行**：`rename_dir` 遇到目标已存在时先比 canonicalize，两个规范化路径相同就是同一个目录，直接 `fs::rename`（Windows 上实测成功），不再误报冲突。④ **菜单的空判据问后端**（`dir_empty`），不再数 `list_notes(300)` 的行——列表截断会让深层空目录被误判。⑤ **`tree.toml` 同父键先合并**：`rename_path` / `remove_path` 改写前先按父层去重（后出现的同键 unique 名字并入先出现的），否则一条改名能留下两条同 `parent` 的层，下次 `save` 按整条替换时其中一条的顺序会被静默吃掉。⑥ **版本快照落不下时回队**：`versions::落待落` 中途失败把剩余的 `待落` 按原顺序推回队列，下个周期重试，不再丢后半批 |
